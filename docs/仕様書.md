# ラズパイ側 在庫管理システム仕様書（Python担当向け）

## 1. 役割と全体像

ラズパイは本システムの「心臓部（サーバー・データベース）」です。以下の3つの役割を持ちます。

1. **M5StickCからの出庫データ受付（API / MQTT）**
   * M5StickCから送られてくる出庫データ（HTTP POST または MQTT通信）を受け取り、在庫を減らして履歴を残す。

2. **PC向けWebサイトの提供（画面・UI）**
   * 部品の検索、マップ・保管場所の確認。
   * 入庫・出庫登録（共通化UIにて、部署選択 ➜ ソートされた従業員選択により実行）。
   * 発注点割れ（「発注してください！」）の警告表示および発注済トグル。
   * 履歴のCSVダウンロード。

3. **データ管理**
   * 在庫データと入出庫履歴データの更新・保存。

※Pythonの軽量Webフレームワーク（Flask）を使い、APIもWeb画面も1つのプログラムで実装します。

## 3. 実装する機能と通信仕様

### ① M5StickC連携機能（出庫受付）

M5StickCからの出庫通信は、**HTTP REST API** と **MQTT通信** の両方を受け取れるハイブリッド構成とします。

#### A. HTTP POST 方式
* **URL**: `POST /api/checkout`
* **受け取るデータ（JSON例）**:
  ```json
  {
    "user_name": "山田太郎",
    "department": "製造部",
    "part_id": "AB-1234",
    "quantity": 2
  }
  ```
* **ラズパイ側の処理**:
  1. `part_id` の部品を探す。
  2. 在庫数から `quantity` を引く（在庫不足時はエラーレスポンス）。
  3. 入出庫履歴ログに1行追加する。
  4. M5StickCへ成功レスポンス（`{"status": "ok"}`）を返す。

#### B. MQTT 通信方式（ラズパイ実機向け拡張）
* **トピック**: `degimono/checkout`
* **ペイロード**: 上記JSON形式と同様
* **ラズパイ側の処理**: ラズパイ上のブローカー（Mosquitto等）を介して `paho-mqtt` でメッセージを受信し、上記と同様の出庫減算処理を実行。

### ④ 履歴CSVダウンロード機能

* **URL**: `GET /download/history.csv`
* **動き**: 画面右上の「入出庫履歴.csv出力」ボタンを押すと、Excelで文字化けしないUTF-8(BOM付き)形式でCSVファイルがダウンロードされる。
* **列**: 日時, 種別, 品番, 品名, 変動数量, 発注数, 作業者名, 使用部署, 備考
  * 変動数量は在庫の増減を符号付きで出す。入庫・登録はプラス、出庫はマイナス、発注は在庫が動かないので `0`。列を合計すると在庫の増減になる。
  * 発注数は発注の行にだけ出す（ほかの行は空欄）。
  * 履歴のデータには数量を正の数のまま保存し、符号はCSVに出すときに付ける。

## 6. 2026-10-21 方針決定事項（第2・3章より優先）

画像（`発注管理イメージ画面.png`、`入出庫管理イメージ画面.png`、各フロー図）に合わせて以下の方針とする。

### 6.1 発注導線（入出庫管理画面 → 発注管理一覧）
* 在庫数 ≦ 発注点 かつ 未発注 の部品には、入出庫管理画面に **「発注登録」ボタン** を表示する。
* ボタンを押すと、**その部品の情報（品番・品名・在庫・発注点）が入力済みの状態で、発注管理一覧の「未発注」タブ内「発注結果の登録」** が開く。
* 従来の「バナークリックで発注済に切替」は廃止。「発注済」への変更は発注結果の保存でのみ行う（発注点以下になっただけでは変更しない）。
* 本システムは発注計算・業者への発注は行わない（既存システムで実施し、結果のみ登録）。

### 6.2 部品テーブル（画像に合わせる）
発注管理で必要な項目を持たせる。発注関連は別テーブル（発注テーブル）に分けてもよい。

| 項目 | 備考 |
| --- | --- |
| 品番（ID）、品名、在庫数、発注点、使用部署 | 既存どおり |
| 保管場所 | 工場配置図の棚記号（A〜F、部品棚）。マップ画像名は廃止し、配置図上で該当棚をハイライト |
| 発注状態 | `未発注` / `入荷待ち`（入庫登録完了で一覧から外す） |
| 発注数量 | 発注結果登録で入力 |
| 発注担当者 | プルダウン選択 |
| 発注日 | 発注結果登録で入力 |
| 入荷予定日 | 発注結果登録で入力 |

* 発注管理一覧の状態表示: 在庫 ≦ 発注点 → 「要発注」（橙）、在庫 ＞ 発注点 → 「発注不要」（緑）。
* 入荷待ちは入荷予定日順に表示。分納なし。

### 6.3 保管場所・工場配置図
* 保管場所は棚記号（A〜F、部品棚）で管理する。
* 入出庫管理画面に工場配置図（加工エリア、組立エリア、A〜F、部品棚）を固定表示する（実際の写真・配置図に差し替え可能な構成）。

### 6.4 入庫フロー（画像準拠）
1. 入出庫管理画面の「発注管理を開く」→ 発注管理一覧の「入荷待ち」タブを表示。
2. 入荷した部品の行で「入庫登録」をクリック → 入出庫管理画面に該当部品が表示される。
3. **入庫担当者は初回のみ設定し、「入荷登録を終了」まで保持**（連続登録時は再選択不要）。
4. 実入荷日・入荷数量を確認し「入庫登録を確定」。
5. 在庫を加算し、入荷待ちから外し、更新後の在庫を表示して発注管理一覧へ戻る。入庫・発注の記録は履歴に保存。
6. 「入荷登録を終了」で担当者設定を解除。
* 従来の「入庫（＋）／出庫（−）モード切替・数量ステッパー」による手動入庫は、この入庫フローに置き換える。

### 6.5 担当者の入力方式
* 担当者（発注担当者・入庫担当者）は **プルダウン選択** とする（第2章③の従業員マスターを利用、五十音順）。
* 画像の「社員番号または社員名」入力欄はプルダウンに置き換える。

### 6.6 M5StickC：QR読取順（QRコード作成手順書に準拠）
社員QR → 部署QR → 部品QR → 個数QR → 確認画面（A: 決定 / B: 取消）。
`出庫フロー.png` の読取順（社員→部品→数量→部署）は、手順書に合わせて修正する。

#### 6.6.1 QRの中身（2026-10-28 決定）
QRの中身は1行で「項目名,値」とする。項目名と値はカンマで区切る。社員IDは入れない。

| 種類 | 中身 | 例 |
|---|---|---|
| 社員 | `社員名,氏名` | `社員名,山田太郎` |
| 部署 | `部署名,部署名` | `部署名,製造部` |
| 部品 | `品番,品番` | `品番,AB-1234` |
| 個数 | `個数,数` | `個数,5` |

* M5は項目名で何のQRかを判定し、読取順と合わなければエラー音を鳴らして進まない。
* 出庫API（`POST /api/checkout`）には社員IDを送らず、氏名（`user_name`）で社員を特定する。
* QRは `QRコード作成.xlsx` で作る（種類ごとのシートに値を入れて印刷する。Microsoft 365 の Excel とインターネット接続が必要で、QRの中身は外部サービス api.qrserver.com に送られる）。
* Excelが使えないときは `qr_generator.py` でも作れる（`--html` で印刷用の一覧、`--demo` でPNG一括、1件だけなら `--label` で項目名を指定）。
* **QRの文字列については、「QRコード作成手順書」（`docs/QRコード　作成手順　.docx`）の3節「QRコードの文字列ルール」（`USER,1001,山田太郎` など）は無視してよい。** この節の決まりを優先する。読取順と画面の動きは引き続き手順書に従う。

### 6.7 発注点アラート（採用）
* 出庫確定後、更新後の在庫が発注点以下の場合、**M5StickCでアラート音とメッセージを表示**する（APIレスポンスにアラート有無を含める）。
* 同時に、PCの発注管理一覧の「未発注」に対象部品を「要発注」として反映する。
* 発注点以下になっただけでは「発注済」に変更しない。

### 6.8 決定事項（担当者プルダウン・テーブル構成）
* **担当者プルダウンはまず「部署選択 → 従業員（五十音順）」の連動式で実装する。** 将来、従業員のみの単一プルダウンへ切り替える可能性があり、切替は部署プルダウンを外して全従業員を五十音順で出すだけで済む。切替を容易にするため以下に注意する。
  * 従業員マスターに **従業員ID（社員番号）と所属部署** を持たせる（同姓同名対策、および履歴の「使用部署」を従業員マスターから引けるようにするため）。
  * APIは従業員名ではなく従業員IDで受け取る設計にし、部署はサーバー側で従業員から導出する。
* **発注情報は部品テーブルとは別の「発注テーブル」に分ける**（発注の履歴を残すため）。
  * 部品: 品番、品名、保管場所、在庫数、発注点、使用部署
  * 発注: 発注ID、品番、発注数量、発注担当者、発注日、入荷予定日、状態（`入荷待ち` / `入荷済`）、実入荷日、入庫担当者
  * 「未発注」は入荷待ちの発注が存在しない状態から導く。入庫確定で状態を `入荷済` にし、入荷待ち一覧から外す（レコードは履歴として残す）。
  * 6.2の部品テーブルの発注関連項目（発注数量・発注担当者・発注日・入荷予定日・発注状態）は、この発注テーブルに置き換える。

### 6.10 部品（新商品）の登録（2026-10-21 追記）

これまで部品は初回のデモデータ投入でしか入らなかった。運用中に新しい部品を Web 画面から登録できるようにする。

#### 6.10.1 画面
* 入出庫管理画面のヘッダー（「発注管理を開く」の隣）に **「部品登録」ボタン** を置き、押すと部品登録画面を表示する。
* 入力項目（担当者以外は部品テーブル 6.8 の項目に対応）:

| 項目 | 入力方法 | 必須 | 規則 |
|---|---|---|---|
| 品番 | テキスト | ○ | 重複不可。40文字以内。空白と `/ \ ? # %` は使用不可（URL・QRで使うため） |
| 品名 | テキスト | ○ | |
| 保管場所 | プルダウン | ○ | A〜F、部品棚（6.3 の棚記号）。選択すると工場配置図に該当棚をハイライト |
| 初期在庫 | 数値 | ○ | 0以上の整数。初期値 0 |
| 発注点 | 数値 | ○ | 0以上の整数。初期値 0 |
| 使用部署 | テキスト | 任意 | 既存の表記（例: `製造部、設備保全課`）に合わせる自由入力 |
| 登録担当者 | 部署→従業員プルダウン | ○ | 6.5 と同じ連動式 |

* 登録成功時はメッセージを表示し、入出庫管理画面へ戻って登録した部品を表示する（続けて登録できるよう、登録画面に留まる選択肢も用意する）。
* エラー（品番重複・必須未入力・不正な数値）は画面上部のトーストに理由を表示し、入力内容は消さない。

#### 6.10.2 API
* `POST /api/parts`（JSON）: `part_id`, `name`, `location`, `stock`, `reorder_point`, `departments`（任意）, `employee_id`
  * 成功: HTTP 201 `{"status":"ok","message":"…を登録しました","part":{…}}`
  * 失敗: 400（入力不備）／409（品番重複）。形式は既存API同様 `{"status":"error","message":"…"}`
* `GET /api/locations`: 選択可能な保管場所（A〜F、部品棚）の一覧。画面のプルダウンに使う。

#### 6.10.3 データ・履歴
* 部品テーブルへ1行追加する（テーブル構成の変更なし。既存DBはそのまま使える）。
* 履歴に種別 **`登録`** で1行追加する（変動数量＝初期在庫、作業者＝登録担当者、備考＝「新規部品登録（初期在庫 n、発注点 n）」）。CSV出力にも含まれる。
* 登録直後に在庫 ≦ 発注点なら、通常どおり発注管理一覧の「未発注」に「要発注」として表示される（6.7）。

#### 6.10.4 対象外（今回やらないこと）
* 登録済み部品の編集（品名・発注点などの変更）、削除。
* CSV／Excel での一括登録。
* 部品QRコードの作成（M5用のQRは `qr_generator.py` で別途作成。登録した品番を `品番,<品番>` の形でQRにする。6.6.1）。

#### 6.10.5 確認が必要な前提（変更があればここを直す）
* 品番の形式に、上記の「使えない文字」以外の制限は設けない（英数字・ハイフン以外も可）。実際の品番ルールが決まっていれば形式チェックを追加する。
* 登録担当者の入力を必須にしている（履歴で誰が登録したか追えるようにするため）。
* 編集・削除が必要になった場合は、誤登録の修正手段として別途追加する（現状は DB を直接操作するしかない）。
