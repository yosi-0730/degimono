# Node-RED 自作用の方針

完成品（`flows.json`、`make_flows.js` で作る）と同じものを、自分で作って Node-RED を覚えるための方針。ここには何を作るかだけを書き、作り方は決めすぎない。

## ねらい

- データは Node-RED のコンテキストに JS のオブジェクトで持ち、DB と SQL を使わない。追加のノードも要らない。
- 1つのノードには1つの仕事だけをさせ、フローの図を見れば流れが分かるようにする。

## ノードの分け方

- コンテキストの読み書きは change ノードで行う。「データを読む」で `global.degimono` を `msg.db` に出し、書き換えたら最後に「保存する」で `msg.db` を `global.degimono` に戻す。
- 何度も使う処理は「共通処理」タブに1つずつ置き、link call で呼ぶ。例: 部品に状態を付ける、履歴に残す、履歴一覧を作る
- 分岐（見つからない、在庫が足りないなど）は switch ノードで行う。
- 決まった形の値や応答（履歴に渡す値、エラーの応答）は change ノード（JSONata）で作る。
- function ノードは「部品を探す」「在庫を減らす」のように、名前を一言で言える仕事だけをする。

例: 出庫

```
[http in] ─┐
           ├→ [出庫の値を読む] → [データを読む] → [従業員と部品を探す] → <出庫できる？> ─OK──→ [在庫を減らす] → [履歴の値] → (履歴に残す) → [保存する] → [結果を作る] ─┬→ <返し先は？> ─HTTP→ [http response]
[mqtt in] ─┘                                                                ├入力の誤り→ [400 の応答] ──────────────────────────────→┤        └MQTT→ [宛先] → [mqtt out]
                                                                            ├従業員なし→ [404 の応答] ──────────────────────────────→┤
                                                                            ├部品なし──→ [404 の応答] ──────────────────────────────→┤
                                                                            └在庫不足──→ [409 の応答] ──────────────────────────────→┘
                                                                                                                       [結果を作る] → <発注点以下？> → [通知文を作る] ─┬→ [宛先] → [mqtt out]（degimono/alert）
                                                                                                                                                                    └→ [websocket out]（/ws/alert）
```

## 前提

- 画面は `flows_screen.json`（「画面」タブだけ）を読み込んで使う。HTML は作らない。`make_flows.js` を実行すると `flows.json` と一緒にできる。
- 画面は下の API をそのまま呼ぶので、URL と返す JSON の形は完成品と同じにする。
- ラズパイの `~/.node-red/settings.js` で `contextStorage` を `localfilesystem` にし、再起動してもデータが消えないようにする（`pm2 restart node-red`）。ファイルへの保存は既定で30秒ごと。
- ラズパイは JST なので、日時は JS の `Date` をそのまま使ってよい。

## データ

グローバルコンテキストに置く。項目名をこのとおりにすると、画面とそのまま合う。

| 種類 | 項目 |
|---|---|
| 従業員 | id, name, kana, department |
| 部品 | id（品番）, name, location, stock, reorder_point, departments |
| 発注 | id（連番）, part_id, quantity, orderer_id, ordered_date, expected_date, status（`入荷待ち` / `入荷済`）, received_date, received_qty, receiver_id |
| 履歴 | id（連番）, ts（`YYYY-MM-DD HH:MM`）, kind（`登録` / `発注` / `入庫` / `出庫`）, part_id, quantity, worker_id, worker_name, department, note |

- 起動時に、データがなければデモデータを入れる。中身は `make_flows.js` の「デモデータSQL」にある従業員17人、部品6件、入荷待ち3件と同じにする。
- デモデータに戻すボタン（inject）があると、試すときに便利。
- コンテキストから取り出したオブジェクトを書き換えたら、必ず `set` し直す。書き換えるだけでは保存されないことがある。

## 部品の返し方（いくつかの API で共通）

部品を返すときは、データの項目に次の3つを足す。

- `below_point`: 在庫が発注点以下なら `true`
- `waiting_order`: その部品の入荷待ちの発注（いちばん古い1件）。なければ `null`
- `state`: 入荷待ちの発注があれば `入荷待ち`、なければ発注点以下で `要発注`、それ以外は `発注不要`

## API

### 読み込み（GET）

| URL | 返すもの |
|---|---|
| `/api/employees` | `{ departments: [...], employees: [{id, name, department}] }`。従業員はよみ順。部署は `製造部, 開発部, 資材課, 品質管理部, 設備保全課` |
| `/api/locations` | `["A","B","C","D","E","F","部品棚"]` |
| `/api/parts?q=語` | 品番か品名に語を含む部品（上の3項目つき）。品番順 |
| `/api/parts/:id` | 部品1件。なければ 404 で `{status:"error", message}` |
| `/api/orders/unordered` | 入荷待ちの発注がない部品。要発注を先に、その中は品番順 |
| `/api/orders/waiting` | 入荷待ちの発注に `part_name, location, stock, orderer_name` を足したもの。入荷予定日順 |
| `/api/history` | 履歴に `part_name` を足したもの。新しい順に200件 |
| `/download/history.csv` | 履歴の全件の CSV。列は `日時,種別,品番,品名,変動数量,発注数,作業者名,使用部署,備考`。変動数量は在庫の増減で、入庫・登録はプラス、出庫はマイナス、発注は0。発注数は発注の行にだけ入れる。Excel で文字化けしないよう先頭に BOM を付け、改行は CRLF |

### 登録（POST）

| URL | 受け取るもの | すること | 返すもの |
|---|---|---|---|
| `/api/parts` | part_id, name, location, stock, reorder_point, departments, employee_id | 部品を足し、履歴に `登録`（備考 `新規部品登録（初期在庫 N、発注点 M）`） | 201 で `{status:"ok", message, part}` |
| `/api/orders` | part_id, quantity, employee_id, ordered_date, expected_date | 発注を `入荷待ち` で足し、履歴に `発注`（備考 `入荷予定日 日付`） | `{status:"ok", message}` |
| `/api/checkin` | order_id, quantity, received_date, employee_id | 在庫を足し、発注を `入荷済` にし、履歴に `入庫`（日時は入荷日＋今の時刻、備考 `発注ID N 入荷`） | `{status:"ok", message, stock}` |

### 出庫（HTTP と MQTT）

- 受け取るもの: part_id, quantity, employee_id または user_name（社員名）, department。QR には社員名だけが入るので、M5 とダミー画面は user_name を送る。従業員は employee_id があれば ID で、なければ名前で探す。
- 確かめる順番とエラー。どれも `{status:"error", message}` を返す。
  1. 品番が空か、数量が0以下: 400
  2. 従業員が見つからない: 404
  3. 部品が見つからない: 404
  4. 在庫が足りない: 409
- 成功したら在庫を減らし、履歴に `出庫` を足す。部署は受け取ったものを使い、空なら従業員の部署を使う。
- 成功時に返すもの: `{status:"ok", message, part_id, part_name, stock（減らした後）, reorder_point, alert, alert_message}`。`alert` は減らした後の在庫が発注点以下なら `true` にし、そのときの `alert_message` は `在庫が発注点以下です。発注してください`。
- 受け口は2つ。
  - HTTP: `POST /api/checkout`（M5 のダミー画面はこちらを使う）
  - MQTT: `degimono/checkout` で受け、結果を `degimono/status` に送る（ブローカーは `localhost:1883`）
- HTTP と MQTT の両方を同じ流れにつなぎ、最後に返し先を分ける（`msg.res` があれば HTTP から来たもの）。
- 出庫後の在庫が発注点以下なら、HTTP と MQTT のどちらから来た出庫でも、M5 に表示する文を `degimono/alert` に送る（QoS 1、retain なし）。
  - 送るもの: `{ part_id, part_name, stock, reorder_point, ordered, text }`
  - ブラウザの M5 ダミー画面（`/m5-dummy`）にも、同じものを WebSocket（`/ws/alert`）で送る。
  - `text` は M5 の画面にそのまま出す文で、行は `\n` で区切る。入荷待ちの発注がなければ最後の行を「発注してください」、あれば「発注済み 入荷予定 10/16」にする。
    ```
    【発注点以下】
    近接センサー
    品番 AB-1234
    在庫 1 / 発注点 2
    発注してください
    ```
- 完成品も同じトピックを受けるので、自作版を試すときは完成品のタブを無効にする（両方動かすと在庫が二重に減る）。

## 確かめ方

- `http://192.168.50.2:1880/app` で、入出庫管理と発注管理の画面がひととおり動くこと。
- `http://192.168.50.2:1880/m5-dummy` から出庫でき、在庫と履歴に反映されること。
- Node-RED を再起動しても、データが残っていること。
- 返す JSON の形に迷ったら、完成品のタブを有効にして同じ API を呼び、返り値と見比べる。

## 完成品

同じ方針で作った完成品が `flows.json`（`make_flows.js` で作る）にあり、ラズパイで動いている。自作版を試すときの切り替え方は `../docs/ラズパイ運用手順書.md` の「8. 自作版を作るとき」にある。
